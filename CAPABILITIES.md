# Endpoint-aware capability contract (CORE-03)

This optional `@ayayaq/vivi/providers/models` module is included in prepared stable `0.4.0`,
which is not yet published. It is absent from the published, immutable `0.3.0` archive. Host
adoption waits for publication and exact registry-byte verification. Root exports and provider
requests are unchanged; this release does not integrate either host.

`src/providers/models.ts` is a pure per-entry normalizer. It has no runtime imports, HTTP, cache,
credential handling, catalog selection, moderation, storage, UI, or agent-loop behavior.
Both hosts retain those responsibilities. Passing a model entry does not establish account
access, a selectable model, or that a routed request will succeed.

## Version 1 schema

`normalizeModelCapabilities({ apiVersion: 1, provider, protocol, model })` accepts `openai` or
`openrouter`, `responses` or `chat-completions`, and one catalog entry with an exact `id`.
An existing selection can use just `{ id }`. This does not fetch, sort, filter, deduplicate, or
replace either host's catalog. Invalid versions, identities, providers, and protocols fail with
sanitized `TypeError` messages. Unsupported or malformed optional metadata remains unknown.

The returned frozen snapshot contains the same version, provider, protocol, and ID, plus:

- `chat`, `tools`, and `stream`: `supported`, `unsupported`, or `unknown`
- `reasoning.support`: the same three states, independently of effort choices
- `reasoning.disable`: support for an explicit disable request, independently of named efforts
- `reasoning.effortSelection`: whether known metadata describes an effort selector
- `reasoning.efforts`: known accepted choices from `none`, `minimal`, `low`, `medium`, `high`,
  `xhigh`, and `max`; unrecognized values are not advertised
- `reasoning.requirement`: `required`, `optional`, or `unknown`; required means reasoning
  cannot be disabled, not that an explicit override must be sent
- `sources`: official documentation URLs and their review dates

`reasoningSelectionSupport(snapshot, selection)` checks the existing provider selection contract:
`{ mode: 'default' }`, `{ mode: 'disabled' }`, or `{ mode: 'effort', effort }`. It does not
transform or send a request. Default means omission and needs no capability assertion; it
does not mean disabled. Explicit disable uses the separate disable capability and is rejected
when reasoning is mandatory. OpenAI needs a documented none choice; OpenRouter can also
document optional reasoning even without an effort selector. Unknown support remains unknown. Hosts still decide whether to
allow an unknown choice, how to migrate a legacy selection, and which defaults to offer.

When a later host maps this contract into the existing provider factories, their
`supportedReasoningEfforts` option also uses `none` as the explicit-disable capability sentinel.
For an optional OpenRouter token-budget model, `disable` can be supported while `efforts` is
empty. A host must map that separate fact to the sentinel explicitly; blindly passing
`reasoning.efforts` would lose disable support. This release changes neither factory.

## OpenRouter interpretation

The [model catalog documentation](https://openrouter.ai/docs/guides/overview/models) describes
input/output modalities and the supported parameter list. A valid complete parameter list can
establish tools or configurable reasoning support; absent or malformed lists cannot. Both
text input and text output are needed to prove text conversation. Explicitly non-text input
or output disproves it. Per-model streaming stays unknown because these fields do not prove it.

The [reasoning documentation](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)
separately describes accepted efforts and the mandatory flag. Null effort metadata accepts all
known gateway choices; a valid list is intersected with known choices. Omitted selectors on a
known reasoning object mean no effort control, not no reasoning. A malformed selector is
unknown. Mandatory reasoning removes none and forbids disable; explicit optional reasoning
allows disable separately from named effort choices. Missing reasoning alone is ambiguous because
dynamic routers also omit it. Exact `openrouter/auto` and `openrouter/free` IDs do not receive a
false non-reasoning assertion from that omission.

These are gateway capabilities for **Chat Completions**. They are not claims about every backing
provider, guaranteed routed behavior, or OpenRouter's separate Responses endpoint. Hosts retain
their existing routing decisions and fallback behavior. No new request option is imposed.

## Provenance and update policy

1. Add or change a static fact only after reading the provider's current official model page
   and any necessary official protocol guide. Record its URL, review date, explicit IDs, and
   endpoint scope. An icon-less list of all API endpoints does not prove support
2. Snapshot IDs must appear in official documentation; never expand aliases by pattern. An
   unverified model, effort, protocol, or field stays unknown. Do not infer account access
3. Add a regression fixture for the fact and any demonstrated CLI/desktop difference. Keep
   reasoning existence, effort availability, mandatory behavior, default omission, and explicit
   disable separate. Gateway metadata does not prove universal backing-provider support
4. Documentation can change. Facts are a reviewed release snapshot, not runtime discovery.
   Recheck changed rows before a release; contradictory evidence downgrades a fact to unknown
   until resolved. Record updates in a new source commit and new reviewed package version
5. Keep fetch/cache, credentials, names, sorting, filtering, defaults, moderation, and selection
   in each host. Do not add generic registries, runtime catalog HTTP, or policy hooks without a
   demonstrated consumer need

## Optional export and release gate

This release adds one optional export, includes this document in package files,
and verifies new-subpath ESM/CommonJS runtime and strict NodeNext declarations in real installed
archives. Existing root and provider/extension exports are unchanged:

```json
"./providers/models": {
  "import": {
    "types": "./dist/providers/models.d.ts",
    "default": "./dist/providers/models.js"
  },
  "require": {
    "types": "./dist/cjs/providers/models.d.ts",
    "default": "./dist/cjs/providers/models.js"
  }
}
```

Only after that separate module-containing release is published and its registry bytes are
verified should CLI or desktop adopt the subpath. Local packed proofs do not satisfy that
publication gate, and no source archive belongs in either consumer repository.
